# F2: controlled evidence and boundaries

The memory benefit is reproducible, but the proposed primary-key explanation does
not explain it. Early dimension filtering alone rescues the tested failures.
Fact pre-aggregation adds a large benefit on hot, nonunique joins and regresses
all other tested cases relative to filtering plus projection. No production
optimizer rule is implemented by this experiment.

## Design and provenance

Measured source: `84a5fa2`. The three evidence directories contain immutable JSONL
with SQL, complete expected results, errors, operator profiles, initial physical
plans, timing and source/binary hashes. `summary.json` is regenerated by
`python3 experiments/f2-proof/summarize.py`.

- 147 sequential processes, 1,176 SQL states, 256 MiB query cap, 100,000 initial
  synthetic rows. Main matrix: seven arms × three distributions × three seeds ×
  eight states, repeated for nonunique and primary-key joins. An additional
  168-state metadata control uses one distribution and seed.
- Native Rust release binary on an otherwise idle build machine; CPU affinity
  0–7, four scan workers and four Rayon workers. Measurements did not use the
  shared Docker daemon. Infrastructure identifiers are intentionally private.
- Real parse → bind → optimize → physical plan → execution, normal
  `SnapshotScanProvider`, declared storage primary key and snapshot-time estimated
  cardinality (held stale as changes arrive). Settled-result memoization disabled.
- Each pinned query races a writer through a barrier. Workload includes sparse
  and dense updates to join keys, group values, nullable measures, inserts,
  deletes, duplicate replay, stale replay, checkpoint, flush and compaction.
  Every process checks pinned rows, latest committed rows and restart rows
  against an independent versioned model. Successful SQL results are checked
  completely; memory refusals remain failures, never timing wins.
- These are decoded CDC storage events, not the binlog transport/server path.
  One reader and a finite writer batch do not establish sustained ingestion
  throughput, lag bounds or production concurrency. Profiles add overhead to
  every arm. Three seeds are a screening experiment, not a confidence interval.

## Capability ablation

Successful states / attempted states, with replica-like metadata. Each cell has
three independent fixtures and eight successive storage states per fixture.

| SQL form | Nonunique: uniform | Nonunique: hot | Nonunique: clustered | PK join: all distributions |
|---|---:|---:|---:|---:|
| Ordinary | 0/24 | 0/24 | 24/24 | 72/72 |
| Projection only | 24/24 | 0/24 | 24/24 | 72/72 |
| Early filter only | 24/24 | 24/24 | 24/24 | 72/72 |
| Early filter + projection | 24/24 | 24/24 | 24/24 | 72/72 |
| Fact pre-aggregation only | 24/24 | 24/24 | 24/24 | 72/72 |
| Fact pre-aggregation + early filter + projection | 24/24 | 24/24 | 24/24 | 72/72 |
| Identity derived table | 0/24 | 0/24 | 24/24 | 72/72 |

The identity arm rules out adding a derived-table boundary alone as the rescue.
Projection has a narrower rescue than either early filtering or factorization.
Both filtering and factorization independently avoid the observed memory failures.
**Factorization is not necessary to obtain all answers in this matrix.**

Physical profiles explain the intermediate work. For uniform data, seed 41017,
phase 1, projection-only joins 902,517 rows before the outer filter reduces them
to 4,084. Early-filter-only scans 437 dimension rows and permits the existing
join/aggregate fusion. This is a predicate-placement change with a consequential
plan change; the experiment does not isolate filtering from that fusion.
Fact-only instead reduces the fact side to key groups while leaving the filter
above the join. Initial physical plans and per-state profiles are retained for
inspection; profile reservation samples are not process peak RSS.

The metadata control (exact/estimated cardinality × key present/absent) has the
same success/refusal pattern in every combination for its uniform fixture.
Supplying a primary key does not itself fix the current plan. This small control
is not evidence about all metadata interactions.

The old experiment's nullable-membership failures are **not rescued or retested
here**. The old successful rewrites covered joins only. Its ordinary join used
`k`, while the storage primary key was `id`; it was not a primary-key join.
The new PK matrix changes the equality to reference `id` explicitly. Its ordinary
queries already fit the memory ceiling.

## Cost: regressions measured before integration

Baseline below is early filter + projection, which returns every answer.
Each ratio is baseline time / combined-factorization time: sum phases 1–7
within each seed, then take the median of the three paired ratios. Phase 0 is
excluded to focus on already-mutated storage. A ratio below one is a regression.
Cycle time is elapsed time until both the query and concurrent writer finish;
it excludes the later model assertions and restart verification.

| Join | Distribution | Query ratio (seed range) | Concurrent cycle ratio | Query time change |
|---|---|---:|---:|---:|
| Nonunique | Uniform | 0.848 (0.813–0.848) | 0.930 | 17.9% slower |
| Nonunique | Hot | 3.702 (3.609–3.774) | 2.194 | 73.0% less time |
| Nonunique | Clustered | 0.846 (0.759–0.892) | 0.908 | 18.2% slower |
| Primary key | Uniform | 0.865 (0.803–0.876) | 0.944 | 15.6% slower |
| Primary key | Hot | 0.914 (0.606–0.916) | 0.938 | 9.4% slower |
| Primary key | Clustered | 0.841 (0.807–0.873) | 0.929 | 19.0% slower |

All three seed ratios have the same direction in every row. Timing is still
machine- and workload-specific. The 3.70× result is neither a replacement for
an end-to-end production benchmark nor a general speedup claim. It compares two
successful plans, not successful execution with refusal.

## What catalog metadata actually proves

`crates/pintail-wire/src/engine.rs::build_catalog` attaches storage key column ids
and estimated snapshot cardinality. `crates/pintail-catalog/src/lib.rs` stores
those facts. `crates/pintail-sql/src/metadata.rs::IndexFacts` also carries a unique
flag, but that frontend record is not a general optimizer statistics model.
The binder already uses key facts for functional dependency checks, with guards
for nullable columns. The old limitation's blanket statement about missing
uniqueness facts was inaccurate and has been replaced.

A complete, nonnullable unique key gives at-most-one matching row **only when
join equality respects that key's uniqueness semantics**. Column coverage alone
is insufficient. Numeric comparison can match both text keys '1' and '01'; a
case-insensitive comparison can match two keys distinct under a binary collation.
Partial composite keys and NULL-safe comparisons against nullable UNIQUE columns
have additional multiplicity hazards.

More fundamentally, the specific COUNT/SUM factorization tested here does not
need a unique dimension. For each fact key k, retain `(N_k, C_k, S_k)`: row count,
nonnull measure count, and nullable measure sum. For every matching dimension
row in output group g, add that tuple to g. Duplicate dimension rows add the
same tuple again, exactly as they duplicate the original fact rows. Preserve
all-null SUM as NULL. This proves bag multiplicity for this restricted inner
join and these aggregates, assuming exact arithmetic in the supported domain.

A production rule must additionally preserve fact grouping attributes, residual
predicates, aggregate result types, overflow behavior and comparison semantics.
AVG requires sums and counts, not averaging partial averages. DISTINCT, outer
joins, floating-point reassociation and arbitrary aggregates are outside this
proof. A primary key cannot make an incorrectly transformed aggregate sound.

## Decision

1. Prioritize a bounded dimension-predicate pushdown improvement: it independently
   removes every observed join refusal and exposes existing execution fusion.
   It still needs production optimizer regression tests before integration.
2. Keep factorization as a separate candidate. Its correctness proof must preserve
   multiplicity and aggregate states; its cost decision must consider reduction
   in fact groups, join fanout and dimension selectivity. A declared PK plus a
   stale table cardinality does not estimate those quantities.
3. Do not ship unconditional pre-aggregation or invent a threshold from these
   three distributions. Obtain useful estimates or design a bounded adaptive
   choice, then test fresh distributions, mutation rates and concurrency.
4. Keep nullable membership as a separate unresolved use case.

The defensible claim is a reproducible join-memory improvement with a cheaper
candidate available, plus a selective factorization opportunity. It is not a
proof that source primary keys justify a universally beneficial optimizer rule.

## Independent MySQL check

`oracle-evidence/result.json` records 336 exact comparisons against MySQL 8.4:
all seven forms, both join-key shapes, three distributions and eight transactional
states at 1,000 initial rows. Pintail uses a 2 GiB cap for this semantic check;
this is separate from the 256 MiB capability matrix. The first semantic-check
attempt at 256 MiB encountered a refusal and was stopped, not counted as a pass.
Ten additional MySQL witnesses demonstrate the multiplicity identity and unsafe
key/coercion, collation, composite-key, nullable-UNIQUE, AVG, COUNT, residual and
NULL-SUM transformations. They test semantic premises, not a shipped rewrite.
The oracle container is isolated and removed by the harness.
